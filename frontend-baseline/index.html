Twenty-three patterns, two weights each, no framework.

Every pattern frontend frameworks compete on, isolated on its own page. Each comes as a light page (the floor: what the simplest site needs) and a heavy page (the ceiling: what a demanding app needs). Rebuild them in a framework, then compare what got easier, what got heavier, and what the framework decided for you.

This page ships no JavaScript apart from the five-line theme reader in <head>. A speculation-rules block asks supporting browsers to prerender light pages as you hover them.

Light and heavy

A light page is the minimum the pattern needs: as little JavaScript as the platform allows, no shared state, no edge cases. It measures the floor, meaning the boilerplate a framework imposes before it earns anything. A heavy page adds what real products need: state, errors, caching, keyboard support, performance under load. It measures the ceiling, meaning how the framework holds up when things get complicated.

The twenty-three patterns

  1. Static contentLight: an about page. Heavy: a long document with a table of contents, tables, code, an art-directed image and structured data.LightHeavy
  2. FormsLight: a newsletter form with no script at all. Heavy: validation, async submit, server errors mapped to fields, drafts, a throttled file upload with progress.LightHeavy
  3. Dynamic data and routingLight: fetch a list and render it. Heavy: a client router, URL as state, cache, prefetch, a guarded mutation and an optimistic update with rollback.LightHeavy
  4. Client stateLight: a persisted to-do list. Heavy: a kanban board with undo and redo, derived state, drag and drop, cross-tab sync and timed renders.LightHeavy
  5. 3D and imperative librariesLight: a spinning cube. Heavy: a lazy-loaded scene with controls, picking, instancing, visibility-gated rendering and disposal.LightHeavy
  6. Real-time updatesLight: poll one value every two seconds. Heavy: server-sent events at up to 30 Hz, frame batching, patch versus rebuild, keyed rows.LightHeavy
  7. Media and lazy loadingLight: a responsive hero and lazy thumbnails, no script. Heavy: infinite scroll, a dialog lightbox, deep links, build-time data.LightHeavy
  8. Cross-cutting concernsLight: a theme switch without a flash. Heavy: theme, i18n, a cookie session, protected content and redirect-after-login.LightHeavy
  9. Content pipelineLight: one Markdown file becomes one page. Heavy: a collection with front matter, generated index, tags, tables of contents, search, RSS and a sitemap.LightHeavy
  10. Data gridLight: a sortable, filterable table of sixty rows. Heavy: up to 200,000 rows, virtual scrolling, sorting and filtering in a worker, selection, keyboard navigation, CSV export.LightHeavy
  11. Composite widgetsLight: native details, popover, dialog and datalist, no script. Heavy: ARIA tabs, combobox, menu button and a command palette built by hand.LightHeavy
  12. MotionLight: CSS transitions, entry animations and scroll-driven animation, no script. Heavy: FLIP reordering, enter and leave animations, a spring-loaded draggable, view transitions between layouts.LightHeavy
  13. Offline and installableLight: a web app manifest, install prompt and connectivity indicator. Heavy: a service worker with caching strategies, an offline fallback and an update prompt.LightHeavy
  14. Async consistencyLight: switching tabs keeps the old content until the new content is ready, latest request wins. Heavy: a view composed from three sources that commits atomically, with per-source retry and an optimistic lane.LightHeavy
  15. State across navigationLight: back to the list restores scroll and filter. Heavy: hidden tabs keep scroll, half-typed input and a paused animation, with a destroy-and-recreate mode for comparison.LightHeavy
  16. Server functionsLight: call one server function. Heavy: batching, deduplication, validation errors, an auth-guarded mutation and a live subscription, all over one endpoint.LightHeavy
  17. Sync and local-firstLight: notes that keep working offline and replay when the network returns. Heavy: versions, conflict detection and resolution, and live changes from other devices.LightHeavy
  18. Morphing and streaming HTMLLight: server HTML morphed into the page without losing focus or input. Heavy: a streamed response applied chunk by chunk, and moveBefore versus insertBefore.LightHeavy
  19. Platform navigationLight: cross-document view transitions, render blocking and speculation rules, no script. Heavy: a Navigation API router on real paths with URLPattern, scroll and focus handling.LightHeavy
  20. Error boundariesLight: global handlers that report every uncaught error. Heavy: section-level boundaries with fallback, backoff retry and deduplicated reporting.LightHeavy
  21. ObservabilityLight: Web Vitals measured on the page itself. Heavy: a trace across a click, two requests with Server-Timing and a render, drawn as a waterfall and exportable.LightHeavy
  22. Security hardeningLight: a strict Content-Security-Policy with build-time hashes, and what it blocks. Heavy: Trusted Types, a sanitiser for untrusted HTML, and CSRF on a form.LightHeavy

How to run a comparison

  1. Read the sheet. Each framework has a page under docs/: what it is, how each pattern maps onto it, migration steps, and what to watch for.
  2. Port the light pages first, then the heavy ones. Keep scripts/mock-api.js so every implementation talks to the same server.
  3. Measure the same things. Built JavaScript and CSS per page, lines of code, Lighthouse on the static and dynamic pages, render timings on the state, real-time and grid pages, and the list of decisions the framework made for you.
  4. Write it down. The rubric in docs/README.md keeps notes comparable across frameworks.

What is deliberately not here

No component library, no router library, no state library, no CSS framework. The shared code in src/lib is a few hundred lines and exists only so the pages can be compared fairly. When a framework makes one of those files unnecessary, that is a finding worth writing down.
