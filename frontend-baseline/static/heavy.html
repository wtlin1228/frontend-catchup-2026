Pattern 1 of 23: static content

Survey method

A document-scale static page: a sticky table of contents, eight sections, tables, code, an art-directed image, footnotes, structured data for search engines and a print stylesheet. Content sites are mostly this, and it still needs no JavaScript.

Scope

The survey compares frontend libraries, frameworks and meta-frameworks on the same thirteen patterns, implemented against the same mock API. It does not compare hosting, pricing, or ecosystems in the abstract; those show up only where they change how a page is built.

Each candidate gets its own implementation directory and its own sheet under docs/. The baseline in this repository is the control group: plain HTML, CSS and JavaScript with a build tool and nothing else.1

Light and heavy pages

Every pattern is implemented twice. The light page is the smallest honest version of the pattern. The heavy page adds the concerns a product team meets within a year: errors, caching, keyboard support, large data, lifecycle and cleanup.

A framework that is pleasant on the light page and painful on the heavy page is a framework for prototypes. The reverse is a framework for teams that already know what they are building.
QuestionLight pages answerHeavy pages answer
What does the framework cost before it helps?Bytes shipped, files needed, concepts requiredNot applicable
What does the framework decide for me?Rendering mode, routing conventionData flow, caching, error boundaries
Where does it fight me?Rarely visibleImperative libraries, high-frequency updates, large lists

Rubric

Score each criterion from 1 to 5 and keep a one-line justification. Totals are less useful than the shape of the scores; a framework that scores 5 on rendering and 2 on forms tells you where it will hurt.

Criteria

Floor
Cost and ceremony of the light pages.
Ceiling
How the heavy pages held up: performance, complexity, escape hatches.
Rendering
Static, server, client and streaming options, and how they mix.
Data
Loading, caching, invalidation, mutations, optimistic updates.
Forms
Progressive enhancement, validation, server round trips.
Interop
Imperative libraries, web components, workers.
Tooling
Build, dev server, TypeScript, tests, debugging.
Ecosystem and longevity
Maintenance, governance, hiring, migration history.

Procedure

  1. Read the framework's sheet in docs/ and note the current version.
  2. Scaffold with the framework's official starter. Record the dependency count.
  3. Port the light pages in order, then the heavy pages. Keep scripts/mock-api.js.
  4. Measure. Fill in the rubric the same day, while the pain is fresh.
  5. File the implementation and the sheet. Repeat for the next candidate.

Threats to validity

The baseline author's habits leak into every port. Light pages favour frameworks with a static-first default; heavy pages favour frameworks the implementer already knows. Versions move monthly, so date every measurement. Lighthouse on a laptop says little about a phone on a slow network.

How to reduce them

Have two people port the same framework independently for at least one candidate. Use the official starters without modification. Record versions in the sheet. Run Lighthouse with CPU and network throttling.

Glossary

Hydration
Re-running component code in the browser to make server-rendered HTML interactive.
Island
An interactive component inside otherwise static HTML, with its own loading strategy.
Resumability
Serialising application state so the browser can continue without re-running the app.
Signal
A reactive value whose readers are tracked so that only they update when it changes.
Meta-framework
A framework around a UI library that adds routing, data loading, rendering modes and a server.
