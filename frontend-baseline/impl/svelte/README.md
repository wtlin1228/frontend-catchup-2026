# Svelte port

Svelte 5.57 (runes) on Vite 8. Same mock API, same public assets and the same stylesheet as the baseline (through the `@baseline` alias), same element ids, so the baseline's checks and measurement script run against this build unchanged. Set up exactly like `impl/react`, so the two ports compare with each other as well as with the baseline.

```sh
cd impl/svelte
pnpm install
pnpm dev                     # http://localhost:5173 with the mock API
pnpm build && pnpm preview   # the production build
```

From the project root, `pnpm compare --only svelte` rebuilds this port, opens its pages, runs the flows its pages support and the on-page measurements, and refreshes `docs/results.md` with this column next to the baseline's and the other ports'. The baseline's `tools/smoke` scripts also run against it directly, since the URLs and element ids are the same.

## Ported so far

Patterns 1 to 4 and 14 light and patterns 2, 3, 4, 6, 10, 11, 12 and 14 heavy: `static/light.html`, `forms/light.html`, `forms/heavy.html`, `dynamic/light.html`, `dynamic/heavy.html`, `state/light.html`, `state/heavy.html`, `realtime/heavy.html`, `table/heavy.html`, `components/heavy.html`, `motion/heavy.html`, `async/light.html`, `async/heavy.html`, plus a hub. Links to pages that are not ported lead nowhere in this build; the posts app's "New post" route sends you to the baseline's login page, which this build does not have, so sign in on the baseline first (`pnpm preview` at the project root) when you want to try publishing.

## What Svelte decided for me

- Client rendering, as with React: every page is an empty `<div>` until the runtime and the component have run; the light pages need SvelteKit's prerendering to be what they are in the baseline. The runtime is a quarter of React's, which is the difference that shows on every light page.
- Fine-grained updates from the compiler: the board's 606-card re-render beats both the baseline and React with no work on my part; the filter keystroke does not, and the keyed `each` over a derived view is the first thing to profile.
- Effects run after the DOM is updated, so timing a render is one `$effect` reading the derived list, where React needed `useLayoutEffect` and a ref.
- Deep `$state` for the to-do list (mutate in place) and `$state.raw` for the board (immutable snapshots for history): the choice is explicit and local.
- The widgets: `export function reset()` is a component method and `bind:this` on a component gives the instance, so the palette resets its combobox without remounting; `<svelte:document onkeydown>` is the global shortcut; the menu awaits `tick()` before focusing an item in the just-unhidden list; the a11y warnings for `role="option"` and `role="menuitem"` with click handlers are silenced per element.
- The async pages use async Svelte (`await` in `$derived`, `<svelte:boundary>` with `pending` and `failed` snippets, `$effect.pending()`), still behind `compilerOptions.experimental.async` in 5.57. Light: the old list stays while the new `$derived` resolves, and the naive mode is the classic `{#await}` block. Heavy: three async deriveds inside one boundary commit together; stream mode keys each part's boundary by post.
- The motion page is where Svelte ships the most: `animate:flip` and `transition:scale` on the keyed list replace the FLIP and WAAPI code, `Spring` from `svelte/motion` replaces the hand-written integrator (`preserveMomentum` keeps the fling), `prefersReducedMotion` is a built-in media query. Only the layout switch still calls `document.startViewTransition`, with `await tick()` inside the callback so the DOM changes within it.
- The contact form is one `$state` object bound to the fields (`bind:value`, `bind:checked`), an `errors` object and a `pending` flag; validation reads the DOM's validity from the event target, the draft is saved from the form's `input` event as in the baseline, and `$state.snapshot` turns the proxy back into plain data for storage. Nothing framework-specific was needed for the pending state or the server errors: assign and the DOM follows.
- The grid: `$state.raw` for the 200,000 rows and the typed-array order (a deep proxy over them would be the mistake), the window a `$derived` slice keyed by position, the query an effect over the state it reads. The worker sorts, so the framework's share is a 30-row window in 1 to 3 ms, as in the other three.
- The posts app needed no library: a forty-line hash router is a `$state` object in a `.svelte.js` module updated on `hashchange`, each view is a component, and the baseline's `api.js` (cache, prefetch, invalidate) is imported as is. The whole page is 6 kB gzip on top of the runtime, against 43 kB for React's router and query library.

## Where I fought it

- `export const` is not allowed in a runes-mode instance script, so the pattern list moved to a module.
- The edit dialog's uncontrolled fields reset through `{#key editing?.id}`, as in the React port, and the save handler reads the DOM.
- Drag-and-drop hover classes are toggled imperatively on `currentTarget`, as everywhere else.
- Focus after a keyboard move is restored by id in the effect; keyed blocks keep the element but moving it still drops focus in this Svelte version.
- The inline theme script and the `<title>` stay in each HTML file; a component runs too late for the first and `<svelte:head>` would add a second title.
- Toasts still come from the baseline's `toast.js`; a Svelte version is a module-level `$state` array and one component.
- Four things the experimental async needed by hand. A batch that starts async work is held back whole, tabs and markers included, so the tab highlight and the stale marker get a `flushSync` batch of their own. Batches committed in the order their promises landed, so a superseded post could overwrite the newer one; the parts await their requests through a version guard that never resolves a superseded request, as the baseline's version check does. A boundary leaves its failed state only through `reset()`, so a part that failed for the previous post kept showing it until the parts were keyed by post. And after a superseded batch, the derived read from an event handler was still the superseded post while the DOM showed the latest, so the like handler checks the derived against the prop and re-reads from the cache.
- `$effect.pending()` counts the promises of the boundary it is read in, so with an error boundary per part it can only dim one part at a time; the view's marker is a flag. A log written from effects inside the parts must be written under `untrack`, or every part's effect depends on the log it writes and loops.
- Effects track every signal they read: the list's fetch effect set its status from the previous `data`, which made it depend on `data` and refetch after each response. `untrack` fixed it, and it is the kind of loop the compiler cannot warn about.
- Focus after `sent` changes needs `await tick()`, since the form is still hidden when the assignment returns.
- The grid's query effect writes `active` and reads it to clamp it; without `untrack` around the apply, that read makes the effect depend on `active` and every arrow key re-queries 200,000 rows.
- `bind:this` targets must be `$state` in runes mode, or the build warns and the focus call after a navigation sees `undefined`.
